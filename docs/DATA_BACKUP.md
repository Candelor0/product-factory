# 生成应用数据备份与恢复协议

日期：2026-10-05。对应 D-033、FR-008/010 与 S4-02/03 的数据备份子项。本文描述当前代码；任务状态及运行验证结论以 [TASKS.md](TASKS.md) 和关联证据为准。

## 范围与界面

项目中的「应用数据备份」面板显示生成应用当前数据版本、顶层数据项数量和快照字节数，提供「导出数据备份」与「选择备份并预览」。数据与源码 ZIP 分别导出；查看面板或导出不会为尚无数据的项目初始化存储。已归档项目可查看、导出已有数据，恢复前须先取消归档。

备份是明文 JSON，包含本项目生成应用已保存的个人业务内容，以及项目名称等来源信息。它不包含固定博客样例数据、源码文件或历史、工作台日志、AI 授权及用量、宿主凭据。它也不包含当前数据存储的历史和请求回执，仅保存当前业务快照。用户可在恢复前先另存当前备份。

选择保存位置前后有有限的疑似凭据扫描，命中会阻断导出，不静默删改内容；这不能识别所有秘密，也不使文件成为匿名或加密备份。应自行妥善保管含个人内容的文件。整个备份与恢复流程不调用模型。

## JSON 文件结构

文件使用严格 UTF-8，当前结构如下。哈希字段均为小写 64 位 SHA-256 十六进制文本，ID 为规范小写 UUID v4。

```ts
type DataBackup = {
  schemaVersion: 1,
  format: 'product-factory-app-data-v1',
  exportedAt: string,                  // 标准 ISO 时间
  productFactoryVersion: string,       // 导出工作台版本
  project: { id: string, name: string },
  storeId: string,
  sourceContentHash: string,
  snapshot: { revision: number, values: Record<string, JSONValue> },
  snapshotHash: string,
  integrity: string
};
```

`snapshot` 采用现有[业务数据协议](PERSISTENT_APP_DATA.md)的规范化方式：对象键排序、数组顺序保留、拒绝危险原型键及非 JSON 值。最多 128 个顶层键、单值 128 KiB、快照 1 MiB、深度 16、节点 20000；revision 为非负安全整数，版本 0 必须为空。整个备份文件最多 1 MiB + 64 KiB。未知字段、未知 schema/format、非法 UTF-8、无效内容或哈希不匹配均拒绝。

三个摘要各有不同用途：

- `sourceContentHash`：对当前 `SourceStore.get(projectId).files` 的 `JSON.stringify` 结果取哈希，覆盖文件路径、内容和文件摘要，不包含源码 revision。
- `snapshotHash`：对规范化 `snapshot` 的 `JSON.stringify` 结果取哈希，包含数据 revision 和全部 values。
- `integrity`：按协议固定字段顺序构造除 `integrity` 外的整个 payload，再对其 `JSON.stringify` 结果取哈希。

导出结果另有整个文件字节的 `sha256`，它与上述内部摘要不是同一个值。完整性哈希用于核对内容，不是签名，不能证明文件来自可信的人；能修改文件的人也能重新计算哈希。同源码内容也不保证业务数据语义一定兼容。

## 导出与文件边界

导出请求包含工作台当前读到的 `expectedRevision`。主进程捕获项目名称/归档状态、存储身份、源码内容摘要和数据快照；通过原生保存对话框选择新 `.json` 文件后，再核对捕获状态和敏感内容。期间数据、源码或相关项目状态变化则停止，取消选择不创建备份。

生成页面和工作台 renderer 都不能通过此接口提交任意宿主路径。保存及选择备份均通过主进程原生文件对话框；程序安装目录和工作台数据目录受保护。

保存复用独占文件发布器：验证绝对规范路径和祖先目录，拒绝符号链接；独占临时文件写入并 fsync，重查父目录身份与内容，以不可覆盖的链接发布到目标，随后清理自己的临时文件。已有目标文件不会替换、删除或跟随。发布后异常只有精确身份及哈希回读确认才返回成功，否则报告 `EXPORT_COMMIT_UNCERTAIN`，用户应保留并核对所选文件。

读取选定备份先验证全部祖先目录、目标普通文件和单一硬链接，使用不跟随链接的有界读取；拒绝管道、设备、超限文件及读取过程中身份/大小/时间变化。两遍受限读取内容一致后才交给协议解析器。这些检查面向受控本地文件流程，不承诺对抗任意恶意本机并发修改的完整系统沙箱。

## 恢复条件与影响预览

当前只支持已有完整有效存储的原位恢复。备份必须与目标满足：

1. 同项目 ID。
2. 同 `storeId`，即同一次初始化的数据存储。
3. 同源码 `files` 内容摘要。

源码 revision 不必相同：编辑后再恢复成完全相同的文件内容，仍可匹配。备份的数据 revision 只是来源信息，不作为恢复后的目标版本。其他项目、重新初始化的存储或不同源码均拒绝；不借备份导入重新建立缺失或损坏的原存储。

选文件前后核对当前状态，解析通过后，主进程计算顶层键的新增、移除、内容变化及相同项数量。界面显示文件名、备份时间、当前/备份数据版本、项数、快照大小和键名；不把业务值正文传给恢复预览界面。用户须勾选整体替换和关闭应用的影响，再点「确认恢复数据」。

完整备份 payload 保留在主进程内存，renderer 只得到随机 `previewId` 与影响摘要；确认只提交项目 ID 和该 token，不能替换 values、版本、哈希或文件路径。一次预览有效期为 10 分钟；选择新预览、取消或主进程退出会使旧预览失效。选定文件在预览后被改写也不会改变待恢复 payload，确认使用已经核对的那一份内存快照。

## 确认、原子恢复与重试

首次确认前重新核对项目、存储、源码和当前数据。随后关闭所属持久本地应用，再次核对状态和预览有效性；关窗期间出现的数据写入、源码变化、归档或取消会阻止恢复。关闭可能丢弃应用中尚未保存的编辑，界面在确认前明确提示。

恢复使用固定的内部请求 ID、`storeId`、`expectedRevision` 和 `expectedHash`，整体替换 values，不能拆成多个 32 项 SDK 提交。新版本恒为当前 revision + 1；即使恢复为空或内容相同，也追加一个新版本。保存前重查当前记录，整份快照一次原子发布，旧 current 进入现有历史。

保留最近 5 份数据历史和最近 256 个提交回执，不重置旧记录、存储身份或初始化标记。恢复前后的源码、AI 用量与授权、固定样例数据均不变；完成后不自动重开应用，也不自动迁移或修复业务结构。历史是有限保留，不替代独立备份。

恢复请求哈希带 `operation: 'restore'` 前缀，与普通数据 `apply` 回执区分。同 ID 不同输入返回冲突；同 ID 同输入先核对回执，再检查旧版本是否仍当前。成功响应同时给出当前 `revision`、最初提交的 `appliedRevision` 及 `replayed`。

若回复丢失或出现不确定提交，界面保留本次 token，允许手动「重试同一次恢复」。主进程沿用原请求，不生成新 ID：

- 原操作已提交：返回回执，不再覆盖，即使随后已有新的业务版本；已知成功的核对不会再次关闭新打开的应用。
- 原操作未提交且当前数据仍匹配：可完成原先那一次恢复。
- 原操作未提交但数据已变化：拒绝旧版本/哈希；不因重试放松存储比较。
- 原回执已超出 256 条保留窗口：原 `expectedRevision` 已旧，拒绝再次应用。

已尝试操作的同 token 核对允许数据版本变化，以便查询已提交回执，但项目/存储/源码上下文仍须一致。不确定时关闭预览不会撤销已提交数据。token 不跨主进程重启保存；过期或重启后应先核对当前数据，新选一次备份属于新的恢复操作，不能当作原请求的回执查询。

## 缺失检测与未覆盖能力

`inspect()` 只读现有 `data/generated` 与配对初始化标记：从未初始化返回空状态，已有文件缺失、腐坏、链接异常或身份不匹配拒绝读取。它不补写初始化标记；初始化中断的恢复仍由原受控读取流程处理。备份及恢复入口不能静默新建空库，也不能用导入绕过原存储的缺失检测。

若外部同时删除生成数据目录及外层初始化标记，新进程无法区分从未初始化与整体被删；本功能不解决这一底层检测盲点。它不是整机灾难恢复、跨机器项目重建或任意文件导入机制。

本轮没有损坏/缺失数据重建、跨项目或跨存储恢复、通用 schema 迁移、图片/附件备份、固定博客样例导入或历史版本浏览恢复 UI。要恢复的结构仍须由使用者结合业务含义核对，校验通过不等于完整业务验收。
