# 开发与验收证据规则

此目录保存真实开发与运行证据。2026-10-02 已有上游离线、Node 自动化、Electron 重开与内部包检查；它们的限制见各次 result.md，不代表完整产品或双平台验收通过。不要创建空报告并将它引用为测试通过。

## 目录约定

使用 `docs/evidence/日期/任务ID/运行编号/`，例如未来某次 S3-02 运行下保存 `result.md`、脱敏日志和必要截图。日期、任务和运行编号使用实际值；本例不代表已有文件。

## 每次记录需要包含

| 字段 | 内容 |
| --- | --- |
| 对应关系 | 任务 ID、需求 ID、验收 ID |
| 时间与执行者 | 实际开始结束时间、执行者 |
| 环境 | 操作系统、CPU、运行环境、网络条件、干净环境与否 |
| 版本 | 真实提交标识；没有提交则写文件清单与适当校验摘要；模型、模板和提示词版本 |
| 输入 | 使用的需求、固定案例与必要测试数据，不保存密钥 |
| 操作 | 实际命令、人工步骤或可复现脚本路径；仅记录真做过的动作 |
| 结果 | 退出状态、输出、检查结论、失败原因和剩余限制 |
| 附件 | 日志、截图、生成产物的相对链接 |
| 判定 | 通过、失败、阻塞或部分完成；不能以“已运行”代替通过 |

自动测试、人工检查、静态分析分别标注。截图能够证明界面状态，不能独自证明数据重启保留或后台行为。测试失败也要保留，不能只存成功截图。

## 脱敏与维护

日志、截图和命令不得包含 API Key、Authorization 头、账号令牌或不必要个人内容。供应商请求标识在需要排查时可以保留，但应检查其敏感性。

模型输出属于待验证内容。记录模型说“完成”不代表任务完成。先检查文件、构建和实际用户操作，再更新任务台账。

若证据丢失或无法复现，标记为需重新验证。不要让历史通过结论无限覆盖之后发生的代码和环境变化。
